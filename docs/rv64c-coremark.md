同版本进一步定位 4 路收益偏低的原因：默认 2/2/2 的取指等待只有 1,174 周期，
队首等待 load 执行却有 40,795 周期，其中 39,561 周期在等待访存响应；
另有 20,799 个 store 队首结构停顿周期。4/4/4 默认配置的 ROB 满周期为 61,607，
比 2/2/2 的 31,590 更多，说明扩大分配宽度后，单条数据访存通路和 32 项 ROB
更容易限制后端。将 2 路 ROB/物理寄存器/LSU 槽同时扩大到 64/96/8，
周期反而增至 272,233，恢复周期也从 11,459 增至 17,892；因此不能仅靠扩容改善 IPC。

`OrderedTileLinkBridge` 原先将每个 D 响应写入重排寄存器，下一拍才送往 LSU。
可选的 `flowTileLinkResponse` 在 D 响应正好属于最老请求时直接转发；
若上游背压或 D 响应乱序，仍由原寄存器保存并按请求顺序输出。

`python3 simulator/gsim/run.py coremark-tune --flow-tilelink-response`
可复测 2 路配置。提前发起本地 store 和让独立 load 越过未排空写缓冲的试验
分别只改善约 0.5% 和 0.3%，还增加时序或内存排序复杂度，未保留。
直通增加 RAM D 到 LSU 寄存器的组合路径；没有 Vivado Fmax 和资源数据时，
仍须将其视作仿真验证过的可选方案，而不是 FPGA 实际运行时间的结论。

继续针对同一 2 路镜像做单变量实验：将回滚宽度从 4 增至 8 项，恢复周期
9,747→4,171，总周期 243,403→237,857（减少 2.28%），CRC/数据类型错误为 0。
`python3 simulator/gsim/run.py coremark-tune --flow-tilelink-response --recovery-width 8`
可复测；`make gsim-backend-recovery8-test` 用独立随机记分板核对 8 项回滚。
回滚宽度会增加 RAT/free-list 更新端口和组合选择，尚无 Vivado 时序数据，
因此仍是可选性能配置；不能仅凭 GSIM 周期数断言 FPGA 上运行时间更短。
访存槽和写缓冲分别由 4 增到 8 项，均得到完全相同的 237,857 周期，故不加大默认容量。
预测表由 256 增到 512 项只节省 74 周期（0.03%），也未扩大正式参数上限。

针对队首 store 的固定气泡，`fastBufferedStoreRetire` 允许**已成功进入保证写入成功的
RAM 写缓冲**的队首普通 store 在接受请求的当拍退休；LSU 同时丢弃原本下一拍才会
交给 ROB 的重复完成。MMIO、原子、PMP 拒绝、未对齐和写缓冲背压仍走原路径。
`python3 simulator/gsim/run.py coremark-tune --flow-tilelink-response --recovery-width 8 --fast-buffered-store-retire`
可在同一镜像复测：237,857→233,947 周期（少 1.64%），零提交周期
58,583→51,919，队首 store 结构停顿 19,482→1,184；CRC/数据类型错误仍为 0。
减少的 store 停顿并不等于总周期收益：队首 load 结构停顿从 4,624 升至 11,555，
等待 load 执行从 20,548 升至 25,146，说明负载依赖与单访存入口更快暴露为限制。
该旁路经 `make gsim-core-fast-store-test` 的 NEMU 差分和完整 GSIM 回归验证。

才能决定是否作为 FPGA 默认配置。

新 OoO 核通过 `OooParams.compressedInstructions` 选择 IALIGN16。启用后，取指器按半字
边界拼接 16/32 位指令，包括跨 64 位取指包的 32 位指令；前端用实际指令长度推进 PC，

进一步尝试把尚未锁存的 load 响应直接旁路到发射/AGU 时，`firtool` 找到两条组合环：
一条经分支恢复与 LSU 当拍取消返回旁路有效信号；移除这条依赖后，另一条仍经
SoC 的内存请求、共享缓存/MMIO 路由与响应有效信号闭合。即使队列响应归属改用
寄存路径，现有 TileLink 接口仍允许后一个组合依赖。因此该实验没有进入性能
对照，所有实验性 RTL 已撤回，保留上述 158,364 周期的锁存完成值旁路配置。
若要实现响应当拍再发依赖请求，须先给相关 RAM 访问建立明确的无 A→D 组合
依赖合同，并验证 FPGA 的 D→唤醒→AGU→A 关键路径。GSIM 生成失败时，
`simulator/gsim/run.py` 现在会额外调用本地 `firtool`，把组合环诊断写入该目标的
`firtool-diagnostic.log`；正常验证不会增加这一检查的耗时。

对链表热点的 `mv s0,a4; ld a4,0(s0)` 又做了可选的重命名别名实验：`C.MV`、
`ADDI rd,rs1,0` 和源操作数之一为 `x0` 的 `ADD`，可让目的寄存器直接引用源物理
寄存器。`mv` 仍占 ROB 项并正常退休；消费指令无需等待它的 ALU 写回。共享物理寄存器
由所有活映射的引用数控制释放，包含同包 RAW/WAW、提交及最多 16 项/拍回滚。
独立 GSIM 记分板 18,000 拍随机流覆盖 3,189 次别名分配；2 路裸核的 NEMU 差分
通过 282 个程序、380,429 次提交。

同一 4 路 CoreMark 镜像由 155,264 降至 **154,851** 周期，仅少 413 周期

对默认配置的调度器加只读计数后，12,792 拍有一个本来可以发射的年轻 RAM load
因较老 store 的顺序约束被拦住；其中 12,331 拍至少存在一个地址尚未记录的较老
store。热点包括 `core_state_transition` 的 `0x800016fa`、`matrix_test` 的
`0x800011ac`，说明这不是仅在启动时出现的队首 load 现象。计数是候选 load 的
阻塞拍数，不能直接视作可节省的总周期。

现在把 store 的“地址已知”和“地址及数据均已备好”分别记录。较老 store 的基址
一旦就绪，执行槽即可先算出地址；即使 store 数据仍未就绪，调度器也能让确认
地址不相交、对齐且位于 RAM 的年轻 load 发射。地址重叠或仍未知时继续阻塞，
store 本身仍须等数据齐备才可提交。相同 4 路 CoreMark 镜像从 155,264 降至
**146,876** 周期（-5.40%），IPC 2.0789108→2.1976361；退休仍为 322,780 条，
程序校验错误为 0，load replay 为 0。年轻 load 的 store 顺序阻塞降至 1,678 拍，
其中 1,091 拍存在地址未知的较老 store。该优化增加每个 ROB 项一位地址有效状态，
Vivado 频率与面积影响仍需上板前测量。Scala 测试与完整 `make gsim-test` 通过，
包括裸核 NEMU 282 程序、380,429 次提交及故意失配检出。与可选 `moveAlias`
同时启用时为 146,445 周期、IPC 2.2041039，比默认新配置再少 431 周期；
组合配置的裸核 NEMU 差分也通过。别名收益仍小，故默认配置只启用提前 store 地址。

继续检查队首 `0x80000bca` 的 6,120 拍：该 `ld` 在到达队首时发起请求，
