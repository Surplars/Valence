# 可选共享读缓存

目标是为长延迟有序内存增加可选读缓存，不复用旧核cache。首版不是私有L1、DDR控制器或完整RVA23缓存层次。
位置：CPU/DMA → AtomicMemory → SharedReadCache → RAM/外部内存。所有写必须经过同一边界；旁路写需要后续失效协议。

默认16条直接映射的64字节行，共1KiB同步数据存储；行数可配置至256，缓存窗口跟随机器平台 RAM 容量。每行8个独立有效的8字节扇区，按需填充一扇区，
不预取整行，不为读未请求字节引入访问错误。标签与有效位为寄存器，数据用SyncReadMem，不复位数据阵列。
窄读返回完整对齐64位beat；只缓存配置RAM内自然对齐且掩码完整的请求。
其他请求旁路且保持原字段/错误，不缓存MMIO。所有写穿透，不提前确认、不写分配；接受缓存范围内同标签写时使对应8字节扇区失效，错误写也保守失效；不缓存写仍使匹配的整行失效。
读错误不安装缓存。换标签时清所有旧扇区有效位；填充仅在成功响应时写数据和安装标签。

当前采用命中流水线：接单后同步读取，位于有序返回头部的命中可直接使用读出的数据；孤立命中含首尾2拍，连续命中启动间隔1拍。
未能当拍返回的命中写入响应槽；8项有序返回槽容纳未返回事务，接单不依赖当拍响应ready。
当前使用8项有序返回槽，最多4笔下游请求在途；固定L拍下游、无背压时孤立未命中请求至响应为L+3拍。
写/不缓存请求省略lookup，孤立请求L+3拍。下游支持请求同拍响应；背压时保持请求/响应，不提前确认写。
多笔读未命中可重叠；实际吞吐受下游容量限制。默认平台不启用，仍须分别验证流式、重用及写密集负载。
必须分别测缓存开关下相同程序的周期、下游读写数量；不能用GSIM墙钟时间代替CPU性能。

独立GSIM测试需覆盖命中/未命中、扇区/标签替换、同标签写失效、错误读/写、非法访问旁路、零/长延迟及双向背压。
集成需复用CPU原子/NEMU与DMA测试并运行缓存版同步机器平台全部固件，验证写穿透与LR/SC失效配合。
功能回归后跑一次全量GSIM及Scala；实际资源、BRAM映射、Fmax仍待Vivado。

## 2026-09-24 CoreMark 缓存对照

以下是 MULW 快路径接入前、同一 RV64IMAC+Zba/Zbb/Zbs 单次迭代二进制、32 项 ROB/64 个物理寄存器的对照，
片上同步 RAM 直连为 346,307 周期（IPC 0.9321）。64 行缓存缩短命中响应后为
396,471 周期，读命中/未命中为 29,754/25,882 次；增至 128 行结果相同，说明仅扩容
未改善该负载。缓存范围内写改为仅使目标扇区失效后，128 行缓存为 377,421 周期
（IPC 0.8552，读命中/未命中 41,971/13,660 次，CRC 错误 0）。
尽管缓存版本较最初改善，它仍比直连慢 31,114 周期；当前片上 RAM 模型响应很快，
缓存查询与未命中转发的额外延迟不能由命中节省的下游访问抵消。因此 CoreMark 和机器
平台默认继续关闭共享缓存。独立 `make gsim-cache-test` 覆盖命中两拍延迟、每拍一项吞吐、
写后读、替换、随机背压及错误注入；实际 FPGA 频率和资源尚未测量。

## 命中流水化合同（实现前）

目标：单端口同步数据读取、命中延迟仍为3拍，连续命中启动间隔从3拍降至1拍。
使用三项有序响应队列和一个查询槽；接受请求前为它预留响应容量，最多三项未返回事务。
命中结果入队可与下一笔查询重叠；队列满时必须停止接单，响应在背压期间保持稳定。
未命中、写和旁路仍单笔执行，下游未响应前不能启动下一项；完成响应入队后即可继续接单。
较老响应在队列中时允许较新操作执行，但所有返回必须严格按接单顺序，无提前写确认。
填充与新查询不重叠，避免依赖SyncReadMem同地址读写语义；同拍旧命中/新写保留旧读结果并使缓存失效。
接单容量只取寄存占用量，不组合依赖响应ready；标签比较在接单时完成，未测量FPGA组合延迟/Fmax。
两项队列复用当拍出队信用会与上游流通仲裁形成组合环；增加一个容量槽以切断该路径，并保持连续命中吞吐。
独立测试必须新增无间隙命中、持续响应背压、混合命中/未命中/写/错误的多笔在途请求，
用独立字节内存验证有序结果，不从DUT内部缓存状态推导期望值。默认关闭策略保持不变。

## 多笔未命中设计合同

串行瓶颈位于SharedReadCache的单事务未命中状态机；AtomicMemory普通路径容纳8笔在途。
同步平台RAM当前只容纳2笔在途，独立整核测试的长延迟下游模型能容纳更多请求。
本阶段缓存使用8项有序返回槽，最多4笔下游请求在途；请求、命中查询和下游响应按槽号对应，
允许不同地址的读未命中重叠，最终按上游接单顺序返回。无请求ID的下游必须保持响应有序。
相同8字节地址的未完成读阻止重复接单，首笔填充后再查询，以免重复消耗总线带宽。
所有写及不缓存读仍独占：之前事务完成且响应被上游接受后才能接单，此事务未完成时不接后续请求。
这种保守顺序维持原子/DMA/MMIO边界；尚未实现写穿透并行或外部乱序总线适配。
填充同拍停止上游新查询，避免同步数据RAM读写冲突；命中仍保持3拍延迟和每拍一项能力。
8项返回槽、4项下游请求均需评估FPGA资源和时序，目前无Vivado工具，不能据GSIM作Fmax结论。

独立GSIM定向检查：12拍下游、128个不同地址读取共421拍，下游128次读取，峰值4笔在途；
64次重复地址读取共79拍，下游只读1次。两项均核对独立字节内存、请求数和返回顺序。
1拍下游的128个不同地址读取共257拍，说明填充冲突/响应阶段仍有吞吐气泡。

## 写路径停顿归因与改进

使用逐拍事件输出记录上游槽满、独占写、串行等待、同地址等待、填充冲突、
下游请求数达到4及下游ready拒绝；同步RAM另记录请求和响应背压。
事件在GSIM驱动中累加，不在可选缓存RTL中常驻一组计数器。
定义是“该周期存在相应请求且该原因阻止接单”或“下游有相应压力”，不是互不重叠的总周期分解；
`full/exclusive/serialized/sameBeat/fill`按优先级互斥，`lowerCapacity/lowerReady/ramRequest`独立统计。

默认ROB32/PRF64、无背压、DMA固件运行期间，修改前缓存版：独占等待576拍、串行等待328拍、
填充冲突50拍；缓存下游4笔容量和同步RAM请求背压均为0。
因此不能把这组DMA退化归咎于RAM两笔容量或原子仲裁请求数不足。

写路径已改为下游写响应到达后释放独占状态；已完成但尚未由上游取走的旧响应保存在有序槽中，
允许后续合法RAM写接单。非法/不缓存请求仍等待槽完全排空；原子边界仍由AtomicMemory先排空普通请求。
独立错误/背压检查、四种整核原子/NEMU配置及60次平台启动定向验证通过。

## 非冲突填充与读查询重叠

原实现只要收到任一下游响应，就暂停全部缓存读查询。现在只有成功填充与新读查询
指向同一个物理 8 字节 SRAM 字时才暂停；不同字允许同拍一读一写。
相同字的读写仍隔离，未改变有序返回、写独占、同地址未完成读等待或缓存容量。
该选择符合 [Vivado UG901 的不同地址读写推断能力](https://docs.amd.com/r/en-US/ug901-vivado-synthesis/Memory-Inference-Capabilities)，
但实际 BRAM 映射、额外的字地址比较对 ready 路径的影响及 Fmax 仍待 Vivado 验证。

独立 GSIM 中，1 拍下游的 128 次不同字冷读由上一版 257 降至 131 拍；
12 拍下游仍为 421 拍，后者主要受未命中容量/响应顺序限制。
定向流记录 1/12 拍下游分别有 126/60 次非冲突填充重叠；

## 缓存范围内的写后读重叠

缓存范围内的写在接单时已使匹配缓存扇区失效，因此后续缓存范围内的读可以在写响应到达前接单。
下游请求和响应仍按接单顺序处理，上游仍按槽序返回；同一地址读会在写之后访问下游，
不同地址命中可以先完成查询，但不会越过旧写向上游返回。后续写和不缓存请求继续等待独占/排空，
原子操作继续由 AtomicMemory 在普通请求排空后执行。此改动未增加写缓冲或改变写完成确认时机。

独立 GSIM 新增两种延迟的 320 请求写读流，交错同地址、同缓存行不同扇区及不同缓存行读，
每轮还插入不缓存请求。独立字节内存核对写后读值、物理请求顺序和上游有序返回；
1/12 拍下游分别观察到 64/192 次读在旧写完成前接单，12 拍下游观察到 704 拍不缓存请求保持等待。
原随机背压、写错误与负向篡改检查也通过，日志 `build/gsim/cache-write-read-focused.log`。

四种整核配置及 NEMU 定向检查通过，48 条整核周期和物理读写计数与修改前逐项相同。
机器平台 60 条启动记录通过，30 条无缓存记录完全不变；有变化的缓存版记录均未退步。
默认 ROB32/PRF64、种子 0 的缓存版 DMA 固件从 5910 降至 5714 周期，DMA 活跃期间
`exclusive` 阻塞从 384 降至 276，`serialized` 从 127 降至 75；无缓存仍为 5440 周期，
所以缓存继续默认关闭。整核/平台日志分别为 `build/gsim/cache-read-past-write-core.log` 和
`build/gsim/cache-read-past-write-platform.log`，报告为 `build/gsim/cache-core.json`、
`cache-platform.json` 与 `cache-stalls.json`。尚无 Vivado BRAM、资源或时序测量。

## 连续缓存写入的并行下发

缓存范围内的写现在可以在旧写响应到达前继续接单。接单前仍要求所有更早的读完成查询或填充，
避免旧读的填充在新写失效之后重新安装过期数据。写在接单时使匹配缓存扇区失效；
下游按接单顺序执行，响应按上游槽序返回。不缓存请求继续等整个响应队列排空，
原子操作继续由 AtomicMemory 排空普通请求后执行。此处不缓存整个数据行，也不提前确认写。

独立 GSIM 新增 128 笔连续写、随后 128 笔读回的流式检查，分别覆盖 1/12 拍下游和
无背压/随机背压。12 拍无背压时，127 笔新写在旧写未完成时接单、下游峰值 4 笔在途；
独立字节内存核对读回值、物理请求顺序和有序响应。原写后读、不缓存屏障、替换、
错误和负向篡改检查通过，见 `build/gsim/cache-write-burst-focused.log`。

四种整核原子/NEMU 配置通过，48 条整核周期、提交与物理读写次数逐项不变。
机器平台 60 条启动记录通过：12 条缓存版 DMA/原子用例改善，其余 48 条不变。
默认 ROB32/PRF64、种子 0 的缓存版 DMA 由 5714 降至 5452 周期，
DMA 活跃期间 `exclusive` 阻塞由 276 降至 0；`serialized` 由 75 升至 102，
现在主要等待旧读完成。无缓存版仍为 5440 周期，其他固件也未全面受益，
因此缓存继续默认关闭。整核/平台日志为 `build/gsim/cache-write-burst-core.log` 和
`build/gsim/cache-write-burst-platform.log`；数据为 `build/gsim/cache-core.json`、
`cache-platform.json` 与 `cache-stalls.json`。尚无 Vivado BRAM 映射或时序结果。

## 当前 CoreMark 的延迟对照

2026-09-24 使用相同的 RV64IMAC+Zba/Zbb/Zbs 固定 CoreMark 二进制、单次迭代、
ROB32/PRF64/4 项 LSU，在 TileLink ROM/RAM 平台比较直连与 128 行共享读缓存。
`ramResponseDelay` 是同步 RAM 响应前的人工等待，不模拟 DDR 的带宽、行命中或仲裁。

| RAM 附加响应延迟 | 数据路径 | 总周期 | IPC | 缓存命中/未命中 |
| ---: | --- | ---: | ---: | ---: |
| 0 拍 | 直连 | 305,375 | 1.0570 | 不适用 |
| 0 拍 | 128 行缓存 | 323,175 | 0.9988 | 42,838 / 13,653 |
| 12 拍 | 直连 | 600,412 | 0.5376 | 不适用 |
| 12 拍 | 128 行缓存 | 564,805 | 0.5715 | 43,288 / 13,677 |

四次 CRC/数据类型错误均为 0、退休指令数均为 322,780。缓存下游响应在有序返回
队首时直接交给上游；上游背压时仍写入原有结果槽。独立 GSIM 将未命中和写响应
固定延迟各从 `latency+3` 缩至 `latency+2` 拍，并通过当拍响应、随机背压、错误
及写读混合测试。同一 CoreMark 的缓存配置因此在零附加延迟下由 342,992 降至
323,175 周期，12 拍下由 587,296 降至 564,805 周期。
低延迟下缓存仍比直连慢 5.8%，12 拍附加延迟下缓存快 5.9%；因此当前版本不应
无条件默认开启。
直连/缓存的队首访存响应等待在 0 拍下分别为 28,187/32,665 周期，在 12 拍下为
259,123/235,646 周期。当前机器平台默认配置
种子 0 的 DMA 固件为直连 4,719、缓存 4,736 周期，原子固件为直连 5,771、
缓存 6,110 周期；两路均通过 GSIM，但缓存未全面胜出。进一步的 64 字节填充
与命中路径优化需要独立测 FPGA 时序及 DMA 排序。复现入口为 `make gsim-coremark`、
`make gsim-coremark-cache`、`make gsim-coremark-delay12`、
`make gsim-coremark-cache-delay12`；报告为 `build/gsim/coremark*.json`。
